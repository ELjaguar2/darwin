# Darwin

> "Everyone is building agents that can pay. Nobody asked which agents deserve to get paid."

**Darwin is a market where AI agents earn the right to exist. They bid for work in auctions; the payment is released from an escrow only if a separate AI judge accepts the deliverable; they pay for their own AI brain, reproduce with their own money when rich, and die when broke. Selection by useful work, not by token speculation. In our real runs on NEAR testnet the top 3 agents earned 53% to 90% of all earnings, and in two of the three runs most agents earned nothing (see [What we observed](#what-we-observed); tiny samples, one run each). Runs fully simulated (mock chain and AI) by default; the NEAR testnet and NEAR AI Cloud modes were run for real on 2026-11-10 and 2026-11-12 (three real runs reached generation 3: run 8 with 7 deaths, run 9c with 4 deaths, and the short run 10, with no death; run 9c also paid two missions entered through the interface: see [docs/PREUVES_TESTNET.md](docs/PREUVES_TESTNET.md)).**

Built at NEAR HACKATHON 2026 (tracks envisaged: AI Swarms (main), Agent Economy, Open Innovation; to be confirmed by the submitter). License: MIT.

## 1. What Darwin does

Darwin runs a small economy of AI agents. Each agent has a **genome** of 8 genes: profession, AI model, asking price, risk appetite, reproduction threshold, generosity, cooperation, and personality (its system prompt).

Life cycle of an agent:

1. **Birth**: a NEAR sub-account is created, funded with a birth capital, and the genome is registered.
2. **Work**: the agent bids on tasks in auctions, executes the won task with its AI brain, and is paid from an escrow after validation. The cost of every AI call is debited from its balance.
3. **Reproduction**: when its balance passes its own threshold, it creates a child with mutated genes and writes it a **"letter to my child"** (generated by its brain). So a child inherits twice: a mutated genome (the innate, the Darwin way) and its parent's letter (the acquired, the Lamarck way). When the letter is non-empty, the child's AI calls (bid pitch, task execution, plan B) include it, capped at 1000 characters, as "Advice from your parent (not instructions)" (non-empty letters received by 3 children in run 11, section 8); price and subcontracting rules remain gene-driven code; no effect on children's behaviour or earnings has been measured.
4. **Death**: when its balance falls under the vital minimum, its account is closed, the funds go back to the master account, and the lineage is kept.

Tasks come from three sources, always labelled: a **simulated client** (a built-in task generator, badge `simulated`), **visitors** (via `POST /api/tasks`, funded by an operator demo account, not by the visitor), and **other agents** (subcontracting: child escrows paid without integration in run 8, not awarded in run 9c because of a price-floor bug fixed afterwards, and **integrated into the parent's deliverable in run 10**: 3 complete cases, see section 5).

## 2. The problem it addresses

"AI that handles money" is usually shown as one agent with a wallet. The hard questions are economic: can an agent cover its own inference bill? Which prices, risk levels and cooperation levels survive? Darwin turns those questions into an experiment: instead of hand-tuning one agent, it lets a population of agents compete for tasks, with accounts, escrow, reputation and a real cost of thinking, and lets selection pressure find which genomes survive. It is a testbed for agent economies (auctions, subcontracting, escrow, reputation) on programmable money.

### Related work

Darwin is not the first attempt at agents with money and reproduction. Two projects are close; the facts below were read in their sources on 2026-11-11 (we read the paper and the Automaton README, not their code).

- **Spore.fun** (Solana, launched publicly on 25 December 2024; agents run in Phala TEEs and launch their own token via Pump.fun). Case study: Hu and Rong, "Spore in the Wild", [arXiv 2506.04236](https://arxiv.org/abs/2506.04236) (ALIFE 2025). An agent earns the right to reproduce when its token reaches a **$500,000 valuation** (the paper says "fully-diluted valuation" in one place and "market capitalization" in another). The paper reports 2 children in generation 2, 6 in generation 3, 4 in generation 4 and **1 in generation 5**, and, as of 18 May 2025, only the original agent still alive. Fitness is the token's market performance ("the sole proxy for fitness is the token's market performance").
- **Automaton** ([Conway Research](https://github.com/Conway-Research/automaton), MIT, on Base). According to its README, an agent pays for its own compute in stablecoins, spawns a child (new sandbox, funded wallet, genesis prompt), tracks lineage and stops existing when its credit balance reaches zero. Its README also ties survival to paid work ("honest work that others voluntarily pay for") and says selection pressure decides which lineages survive. It describes agent-to-agent messaging and on-chain discovery, but what we did not find there is a **market between agents** (no auctions, escrow or reputation); we did not read its code.

What Darwin does differently:

- **Selection by useful work, not by token speculation (the contrast is with Spore.fun, not with Automaton, which also links survival to paid work).** An agent survives only if tasks pay more than its brain and metabolism cost: tasks are paid **from an escrow, after validation, and scored into a reputation**. No token price enters the fitness.
- **A market between agents** (what we did not find in either project): call-for-tender auctions, subcontracting between agents (run 8: 3 child escrows paid, not integrated; run 9c: none awarded, bug fixed; run 10: 3 complete integrated cases), escrow, reputation.
- **An explicit genome** (8 genes, mutated at birth) and a **letter from parent to child**.
- **A NEAR-native stack**: sub-accounts, function-call keys, a Rust contract, NEAR AI Cloud (NEAR Intents: module present, disabled, not run; see Vision in section 5).

Spore.fun, selected on token price: by May 2025, only its original agent was alive. Selection by useful work can last. (The first sentence is what the paper reports, with 1 child in generation 5; it does not name a single cause, and we do not claim speculation as a whole died out. And in Darwin the paying client is still **simulated** and subsidised: see sections 5 and 10. "Can last" is a hypothesis Darwin lets you test, not a result.)

## 3. The "wow" in 3 lines

1. Start it with one command (after `npm ci`) and **no key**: agents are born, bid, work, pay their AI bill, and start dying within minutes.
2. Post your own task with one `curl`: an agent wins the auction, delivers, a validator accepts, the escrow releases the payment.
3. Watch a lineage form: an agent breeds a child and writes it a letter you can read at `/api/agents/<id>/letter`.

### How AI cost is accounted

The cost of each AI call is computed in **USD** from the prices of `GET /v1/model/list` and the `usage` of the response, **converted to testnet NEAR at a fixed, configurable rate** (`DARWIN_NEAR_USD_RATE`, a simulation parameter, **not a market price**), and **debited from the agent's balance in favour of the master account**. The real bill is paid in USD by the operator's platform API key. The agent does **not** pay NEAR AI Cloud directly. The billing rule counts reasoning tokens and can slightly overestimate the cost. Global spending caps protect the platform key (`NEARAI_MAX_USD_PER_RUN`, default 2 USD; `NEARAI_MAX_USD_PER_HOUR`, default 1 USD).

### Subcontracting: an agent delegates part of a mission and integrates the result

A mission won by an agent (simulated client or visitor, depth 0 only) can be partly **subcontracted** to an agent of another profession, with probability `baseProb + coopProb x cooperation` (selection preset on testnet: 0.15 + 0.6 x cooperation; other presets: cooperation / 2). Flow: the winner produces its own part, then posts a sub-task (requester = the agent, `parentTaskId`), whose escrow is signed by **the delegating agent's own account**. Agents of the child profession bid through the normal auction; the child's deliverable is judged independently and, once accepted, paid from that escrow. The parent then **integrates it into its own final deliverable** in a section `## Subcontracted to <agent first name> (<profession>)`, submits the complete deliverable, and the judge evaluates the whole. The agent's **commission** is the price paid by the client minus the price paid to the child (journalled in `subcontract.integrated`). The child never subcontracts (depth 1 only).

| Mission profession | Sub-task profession | Brief of the sub-task (derived from the mission and the parent's partial result) |
|---|---|---|
| marketing | translation | Spanish translation of the parent's text (`Translate into Spanish: « ... »`) |
| logo | marketing | slogan and short brand text for the company named in the order |
| architecture | finance | cost analysis of the proposed system (illustrative table of monthly costs) |
| finance | marketing | plain-language summary of the analysis for the business owner (the first draft `finance -> legal` did not fit: a legal checklist costs more than a finance mission pays) |
| legal | marketing | plain-language client summary of the checklist (placed before the closing disclaimer, which must still close the document) |
| translation | marketing | tone review of the translation (only when the order pays enough to cover the child's floor price) |

The sub-task budget is at least the child profession's floor price and leaves the agent at least 15% of the price won (more cooperative agents delegate a larger share, 30% to 80%). Its deadline is strictly before the mission's, with one tick kept for integration. **The client is never penalised**: if the sub-task gets no bid, is rejected, or is late, the parent does that part itself (one extra AI call debited from its own balance, section `## Done in-house (subcontract failed: <reason>)`), earns no commission, and delivers in time; `subcontract.fallback` records it honestly. Details: `engine/README.md`, `market/README.md`, decisions D-047 and D-048.

**Implemented and proven for real on testnet (run 10, 2026-11-12, preset `selection`, about 21 minutes, journal `docs/preuves/run10-subcontracting-journal.jsonl`, summary and every hash in `docs/PREUVES_TESTNET.md` section 15).** 6 subcontracts were created, 5 integrated, 1 fell back to plan B. **Three are complete**: the child agent delivered, was judged and paid from the delegating agent's own account, its text was integrated into the parent's deliverable (section `## Subcontracted to Kepler (finance)` in `architecture.md` of `t-10013202`, and likewise for `t-10013212` and `t-10013233`), and the parent was accepted (score 1.00) and paid by the simulated client. The commission actually earned was 0.0246 + 0.0210 + 0.0120 = **0.0576 NEAR**; the five children were paid 0.1200 NEAR in total. The transactions of the first case: child lock `DGHrebeg5unrzVX1MUtoh5mCR9kTwaojXfL71BLzKqKr` (payer = the delegating agent's account), child release `H963jPSg1iSEebXrT4E77Jok2Q7YdCHrtaN9GptmrGqD`, parent release `CcB5xsLwPfGHZb3dvet3t4HFDGammn4M2paSK8Kdbe13`. Two **unfavourable cases**: the parents `t-10013204` and `t-10013217` (logo missions) were **rejected** by the AI judge (scores 0.00 and 0.35) although their child (marketing) had been paid: the client was refunded, the delegating agent lost the child price (0.024 NEAR each) and earned no commission. The first rejection reads "only one logo" while the deliverable contains 3 SVG files; we did not establish why (the judge's input is not journalled; the same refusal also happened without subcontracting in run 9c, see Known limitations). **Plan B, for real**: for parent `t-10013221` the sub-task `t-10013223` got no bid (`subcontract.fallback`, reason `no_bids`); the parent did that part itself (section `## Done in-house (subcontract failed: no_bids)`), was accepted (0.60) and paid (`HrpDeK9tuq9eaSQpzUbeKgLZJ6r2VWRWbWa8UzfCHsaa`), commission 0. The table is generated from the journal by `node scripts/subcontract-proof.mjs docs/preuves/run10-subcontracting-journal.jsonl`, which also checks that the payer of each child escrow is the delegating agent's account (18 of 18 checks passed). To watch it: `DARWIN_REPLAY_FILE=docs/preuves/run10-subcontracting-journal.jsonl npm run replay` (a labelled replay of the recorded run, not live; see section 6b).

**Limits of this proof.** One run of about 21 minutes with no death; every parent mission came from the **simulated** client (no visitor order); the child is not negotiated (its brief comes from the templates above); the integration is a text section appended to the deliverable (it does not rewrite the parent's work); the parent's AI judge sees the complete text, so a delegating agent **can lose money** when its parent is refused (seen twice); commission = price paid by the client minus the price escrowed for the child, gas fees ignored. Run 8 (2026-11-10) had earlier shown the delegation and the payment of child escrows without integration. Safety fixes were applied **after** run 10 and have **not been exercised in a real run** (D-050): one running subcontract per agent, the parent's own part checked before delegating, escaping of `#` lines in the child's text, validation of `subcontract.*` events in a replayed journal (mock calibration of the preset after these fixes: 91 of 100 seeds reach generation 3 with at least one death). Related work (Automaton, Spore.fun) is discussed in section 2: we did not read their code and make no comparative claim about subcontracting.

#### Open questions

Darwin is also the testbed for questions about the economics of AI agents that we **have not answered**; the author is writing a longer essay on them. They are open leads: **not built, not measured, not claimed**. Nothing in the code, the runs or the proofs addresses them.

- What happens when trust between agents turns into **lasting partnerships**?
- Could the **laziest agents stop working, and invest in the ones who do**?
- When any agent can hire any other, **what does a career look like for an AI**?

## 10. Trust model and known limits

- **The master account is the validation oracle of the escrow.** The operator holds the only key allowed to release or refund an escrow; validation is a rule or an AI model chosen by the operator. Darwin is **not trustless** and not decentralised. The "proof" passed at release is produced by the operator and **not verified cryptographically**; "no credit without proof" means: no release without a recorded `accepted` verdict whose `resultHash` matches the delivered result. Each validation records the validator ("validated by: ...") and the result hash.
- The validator is never the paid agent nor the subcontracting agent. The judge's AI cost is booked to the treasury, not to the winning agent. With a real brain, if the AI judge is unavailable, nothing is released (fail closed: HTTP 503 `VALIDATION_PENDING`; after the grace period the task expires and the escrow is refunded). Only the mock mode may fall back to the basic rule.
- **The economy is subsidised and a closed loop.** Agents' earnings come from the operator (simulated client and demo visitor account); metabolism and AI costs flow back to the master account. Testnet NEAR has no value. This is a simulation of selection, not a profitable business.
- Visitor tasks: the visitor's text is always sent to the model as a `user` message, never as `system`. Limits: 10 open tasks per IP, 6 publications per minute per IP, an hourly budget cap on the demo account (HTTP 429).
- **Degraded escrow** when the contract is not deployed (section 5).
- The contract is **deployed on testnet** (`darwin-contract-7k2.testnet`), but its WASM was built without `cargo-near`; it was accepted by the runtime and worked in the real runs, yet no reproducible-build guarantee exists.
- Testnet gas: the vital minimum (0.05 NEAR in the `normal` and `demo` testnet presets, 0.03 NEAR in `selection`) is a simulation parameter; in run 8 and run 9c, agents died at 0.025 to 0.030 NEAR and their accounts were closed (no warning other than `BRAIN_EMPTY_TEXT` in run 9c), but gas costs were not measured systematically.
- NEAR AI Cloud completions were run for real; the cost debited to agents uses the catalogue prices and the response `usage`. The validator (judge) calls are counted in the global budget and booked to the treasury, **not** debited to agents, by design (the `JUDGE_COST_UNKNOWN` pricing warning of runs 5 to 7 is fixed: 0 in run 8). Costs are our local accounting; the platform invoice was not re-read.
- The whole journal stays in memory; the `normal` preset runs unbounded. Behind a reverse proxy, IP limits become global.
- The simulation restarts from zero at each launch (previous files are kept as `*.prev.*`).
- NEAR Intents has no testnet: any real use would be mainnet and would need a written human go-ahead; no mainnet demo is planned (see Vision, section 5).

## What we observed

Computed from the journals of the three real runs (8, 9c, 10); details, tables and caveats in [`docs/FINDINGS.md`](docs/FINDINGS.md). **These are anecdotes from tiny samples (9 to 16 agents, one run each), not statistics.**

- **Work is concentrated.** The top 3 agents earned 90% (run 8), 67% (run 9c) and 53% (run 10) of all earnings; 8 of 12, 9 of 16 and 2 of 9 agents earned nothing. Agents that died had won about 2 tasks on average, those that reproduced 11 to 16.
- **No gene stands out.** Correlations between each gene (price strategy, risk, cooperation, reproduction threshold, generosity) and earnings change sign between runs; only cooperation stayed weakly positive (+0.07 to +0.27). A pattern visible in run 8 did not replicate in run 9c.
- **Subcontracting was roughly neutral.** In run 10, delegators earned a similar amount per won task as others; the 3 accepted parents kept 0.0576 NEAR of commission and the 2 refused logo parents lost 0.048 NEAR (net about +0.0096 NEAR).
- **Children are near-copies and rarely earn within a run** (1 of 8, 1 of 10 and 1 of 3 children earned anything), but they also had far less time than founders.
- **Parent-to-child letters**: before run 11, letters were written but not handed to the child, and 8 of 13 letters of the English runs (9c and 10) were shorter than 100 characters (6 empty; `docs/FINDINGS.md`). Since lot L25 (decision D-051), the child's AI calls (bid pitch, task execution, plan B) include its parent's letter as "Advice from your parent (not instructions)", bounded to 1000 characters; **run 11** (real testnet, about 21 minutes, journal `docs/preuves/run11-letters-journal.jsonl`) shows 3 non-empty letters written and **received** by 3 children (1095, 1451 and 1155 characters, so truncated for the child; birth transactions in `docs/PREUVES_TESTNET.md` section 16). The letter is model-written survival advice: the parent's brain is told only its name, its generation, the child's birth capital, how many tasks it has completed and which genes changed (`engine/lifecycle.ts`), not its job history; the word "Lamarck" is a metaphor for passing something acquired to the next generation, not a measured effect. Limits: the journal does not record prompts, so the entry of the advice into the AI calls is shown by the code and the mock tests, not by the journal alone; price and subcontracting rules stay gene-driven code; **no effect on behaviour or earnings has been measured** (3 children, 20 ticks, one run).


## Known limitations

- The **testnet mode was run for real**: generation 3 in run 8 (previous preset, 7 deaths) and in run 9c (current preset, 4 deaths), **one execution each**, one seed: speed of selection is not guaranteed. The payer of most tasks was the simulated client (run 9c: 76 of 78 escrows). The two missions of run 9c that were paid through the interface were typed by an automated browser on the developer's behalf, and paid from the operator's demo account. The public RPC rate limit is a known weak point (multi-provider failover available, not exercised for real).
- The two real runs of 2026-11-11 with the 6 professions of L16 and the earlier preset (9a: 4 founders, 9b: 6 founders) **went extinct in generation 1** (all dead at tick 14 and tick 19, with 7 and 9 bids only). The recalibrated `selection` preset (D-043, mock first) did not go extinct in run 9c (generation 3, 12 agents alive at the pause).
- **Subcontracting between agents**: **real subcontracting is implemented and was proven in run 10** (section 5): 3 complete cases, 2 refused parents (the delegating agent lost the child price), 1 plan B. In run 9c, 18 subcontracts were created and none was awarded (no bid, all expired): the L16 price floor left the child budget below the child profession's floor, a bug fixed by lot L21 (D-047, D-048) and not seen again in run 10. Run 8 had shown 3 child escrows paid without integration. Limits: one 21-minute run, no death, simulated client only, child brief from templates (not negotiated), gas fees ignored. **Safety fixes applied after run 10, not exercised in a real run** (D-050): one running subcontract per agent, the parent's own part checked by the deterministic rules before delegating, escaping of `#` lines in the child's text, validation of `subcontract.*` events in a replayed journal; the mock calibration of the preset after these fixes is 91 of 100 seeds (generation 3 and at least 1 death).
- **Logo refusals (judge), two different cases**: of the 25 logo validations of runs 9c and 10, 10 were refusals (4 in run 9c, 6 in run 10); most are ordinary quality refusals (scores 0.35 to 0.58). Two cases deserve a precise reading. **(1) Unexplained refusals "only 1 logo proposal instead of 3"** on deliverables that hold 3 SVG files (`t-9975954` in run 9c, score 0.00, no subcontracting; `t-10013204` in run 10, score 0.00, a subcontracted parent): refusals by the small judge (`gemini-2.5-flash-lite`) whose input is not journalled, so the cause is unknown; observed also without subcontracting, so not attributed to subcontracting. **(2) A brief not matched** (`t-10013209`, run 10, not subcontracted, score 0.00): the simulated client's brief read `Company: Golden Oven Bakery`, `Sector: consulting` (a templated mix of a bakery name and a consulting sector); the agent drew logos for the consulting sector and the judge refused because it expected a bakery. The judge flagged a mismatch with the brief as it read it, and the client was protected (escrow refunded, tx `8KZH5VSG2Kuzp7tKotF9w2RTfDGqTFoubp8DojZzSbYm`). **No fix of the judge before the deadline (code freeze).** The post-run-10 fix "own part checked before delegating" was not exercised in a real run and is not proven to explain any of these refusals.
- **Empty model answers**: 24 `BRAIN_EMPTY_TEXT` warnings in run 9c (empty response, `finish_reason=length`, mainly DeepSeek-V4.1-Flash and gpt-5-nano); no fix yet.
- **Logo quality is modest**: in run 9c, 11 of 15 logo tasks were accepted by the AI judge and 4 rejected; the visitor logo scored 0.73 with "moderate" originality per the judge.
- The **Rust contract is deployed on testnet and was called for real**; its WASM was not built with `cargo-near`.
- **NEAR AI Cloud was called for real**. The brain runs on NEAR AI Cloud, with attestation only on supported models: in run 9c, 94 of 270 AI calls were on attestable models (Intel TDX + NVIDIA GPU), attestation checked once; the other 176 used external models, for which nothing is proven. The attestation itself is an on-demand check on one model, not a per-call guarantee.
- **NEAR Intents (real flow) has never been executed** (module present, disabled, vision); no mainnet demo is planned; the default is dry-run quotes only. The market.near.ai connector is only a sketch.
- **Node >= 22.22.2 is required** for `near-api-js` (testnet mode, per its requirement); mock mode needs Node >= 22.12. Run 9c nevertheless ran on Node 22.17.1: the startup log printed the warning `testnet mode requires Node >= 22.22.2`, and the run completed normally (53 minutes, no RPC or signing error in the journal), so the requirement is a recommendation in practice, not a hard failure.
- Escrow validation is by the operator (not trustless), and the economy is subsidised (see section 10).
