## Key custody
- Master key: `NEAR_MASTER_PRIVATE_KEY` variable (never in the repository), wrapped in `Secret` from `createChain` onward.
- Agent keys: generated by `generateKey()`, stored in `<dataDir>/keys/<account>.<full|fc>.key` (`data/` folder and `*.key` git-ignored, 0600 permissions on POSIX; on Windows, folder protected by the user's ACLs). The key is written BEFORE the creation transaction (never an account without a key).
- No key in an error message, a journal, an event or the archive; RPC messages are cleaned (`ed25519:[REDACTED]`). Tested.

## Rights: full key and function call key
Each sub-account receives a full key (kept by the engine: transfers, `lock_escrow` with a deposit, deletion on death) and, if a contract is configured, a *function call* key limited to the Darwin contract, to an explicit method list (default `["lock_escrow"]`, never empty because empty = all methods in NEAR) and to a gas allowance of 0.05 NEAR. Protocol limit: a function call key cannot attach a deposit, so it cannot move money; deposits (escrow) are signed with the full key. The function call key is meant for a less privileged agent runtime (currently unused in the engine).

## Spending caps
`SpendPolicy` applies to `transfer`, `lockEscrow` and to a child's funding by its parent (`createAccount({fundFrom})`). By default (`createChain`): 4 x birth capital per outflow, 50 x per hour. An overrun throws `SpendCapError` (`ChainError` code `SPEND_CAP_EXCEEDED`, D-031, distinct from `INSUFFICIENT_FUNDS` so as not to kill an agent). The cap of the `visitors.<master>` account (D-025) is set through `perAccount`.

## Death
`closeAccount`: checks that the beneficiary exists (deleting toward a non-existent account would destroy the funds), deletes the account (balance to the beneficiary), removes the keys, archives. If deletion fails: sweep of the balance minus 0.001 NEAR, `frozen` state in the archive. `swept` is an upper bound (the deletion gas is taken from the balance).

## L3 contract differences taken into account
`registerAgent` sends `record{… genome_hash, genome_json}` (canonical JSON, hash checked client-side); `refundEscrow` only accepts `rejected`/`expired` (any other reason: error); `addReputation` waits for the callback to finish then calls (integer delta, non-zero, <= 100); `releasing`/`refunding`: `release/refundEscrow` wait for the final state (10 probes of 1 s) and `getEscrow` sees them as `locked`; `lockEscrow` internally chains `reserve_task` (signed by the operator, anti-squat of task ids, skipped if the identical reservation already exists) then `lock_escrow` signed by the payer; id reserved for another payer: `ESCROW_EXISTS`. The reputation penalty is accepted after a `rejected` or `expired` refund. Degraded mode applies the same reservation in the local ledger. Note: `MockChain` (shared) is more permissive than the contract (free refund reasons, reputation without escrow); market tests in mock must respect the strict rules.

## minVital = 0.05 NEAR on testnet: enough?
Yes, with margin, under one condition. Gas is paid by the signer; at the highest cited floor price (0.001 NEAR/Tgas): a transfer costs about 0.00045 NEAR (0.45 Tgas), a contract call a few hundredths of a NEAR at worst. Deleting the account returns the whole balance (storage included). But attached gas is **prepaid**: near-api-js attaches 30 Tgas by default, i.e. 0.03 NEAR locked at the 0.001 price, the balance must cover it (the unconsumed part is refunded). `lock_escrow` is the only call signed by an agent (30 Tgas): 0.05 > 0.03 so it stays possible as long as the agent is alive. Chosen value: **keep `minVital = 0.05`**, and do not attach more than 30 Tgas to calls signed by an agent (`GAS_CALL`). If the RPC reports a gas price above 0.001 NEAR/Tgas, raise `minVital` to 0.08. The testnet metabolism (0.002 to 0.004 NEAR/tick) far exceeds the gas of a grouped transfer (0.00045 per 4 ticks). Not measured in real conditions (no key): to be confirmed with a first testnet launch (`gas_burnt` of a transaction visible in the explorer).

## Degraded escrow: safe settlement (D-016)
`releaseEscrow`/`refundEscrow` in degraded mode: lock per taskId (concurrent calls run one after the other, the second receives `ESCROW_SETTLED`), `releasing`/`refunding` status written and saved BEFORE the transfer, back to `locked` if the transfer fails, final status after success. `getEscrow` sees the transient state as `locked`, but a new release is refused until it is resolved. After a crash, `recover()` (called by `checkReady()`) compares the balance of the `escrow.<master>` account with the one noted before the transfer: lowered by the amount, the transfer happened (final state); otherwise back to `locked`. Limit: this comparison assumes the account is only used for settlements; a concurrent deposit during the crash window would make recovery ambiguous (conclusion "not paid"), to be checked by hand in the explorer.
